# atlas-learn contracts — the machine interface

Every skill, agent and script in this plugin reads and writes the files named here, in exactly these shapes. A change to a name or a marker is a change to this file first.

**Evidence policy.** `references/evidence-policy.md` sits above this file: what counts as evidence, what may be calculated, what a visualization may show, how gaps are marked, and which gate enforces each rule. The shapes below carry those rules; where a sentence here and the policy disagree, the policy wins.

Words used below: **main agent** = the Claude session that ran the command; **agent** = a subagent launched with the `Agent` tool (`subagent_type: "atlas-learn:<name>"`); **gate** = a Python script that checks a file and ends with a `RESULT:` line; **plan** = `topics/<slug>/PLAN.md`; **slug** = the topic's short code name.

## 1. Stages and commands

| # | Stage | Command | Starts when | Done when (gate) |
|---|---|---|---|---|
| 1 | `insights` | `/atlas-learn:collect-insights <topic>` | no plan for the slug | plan `## What I want` complete, `tmp/INSIGHTS.md` `Status: Confirmed`, Progress row `[x]` |
| 2 | `brief` | `/atlas-learn:research <slug>` (part A) | insights `[x]` | `tmp/BRIEF.md` `Status: Approved`, insight hash matches, plan `## Modules` = brief modules |
| 3 | `research` | `/atlas-learn:research <slug>` (part B) | brief `[x]` | every module row Researched and Checked ∈ {`[x]`, `[SKIP]`}, `tmp/dossier/00-overview.md` passes `check_dossier.py --overview` |
| 4 | `compose` | `/atlas-learn:compose <slug>` | research `[x]` | `tmp/SITE_PLAN.md` all pages `[x]`, `validate.py` PASS, `tmp/SITE_REVIEW.md` `Verdict: READY` |
| — | `done` | — | compose `[x]` | — |

`/atlas-learn:go <topic or slug> [--all] [--single|--site]` reads the plan (`next_stage.py`) and invokes the skill for the first stage that is not `[x]`; without `--all` it stops after one stage. Stages 2 and 3 run in one session when the user approves the brief with "Approve — start research".

**Format** — what stage 4 builds, from the same template: `site` (default; the multi-page interactive site) or `single` (one self-contained HTML page with condensed content: summary, one part per module, checkpoints, glossary, references, trust footer). The refiner derives it from the insight (`Use`, `Goal`, `Start`); `--single`/`--site` forces it. The live value is the plan header `**Format**`. Size is checked twice and the user is asked when a single page would be too long: after the brief is written (`estimate_size.py` against the 250 KB page budget) and after the page is written (`validate.py` size warning). Switching to `site` reuses everything already researched.

**Slug** = the topic's short code name: kebab-case, `[a-z0-9-]`, ≤ 24 characters, derived from the topic by the main agent in stage 1 and never changed. It names the topic folder `topics/<slug>/`.

## 2. Files

Work is organised by topic. Everything about one topic lives in its folder; the repo root holds only the dictionary of topics.

```
<repo>/
├── index.html                          the topic dictionary — ONE self-contained file; the data is embedded inline in a topics-data JSON block (generated by build_index.py, never hand-edited)
└── topics/<slug>/
    ├── PLAN.md                         short tracker, committed — the only file a human needs to catch up
    ├── topic.json                      metadata for the dictionary (§13), committed
    ├── index.html                      the site's overview page
    ├── pages/                          every other page: modules, synthesis parts, bibliography, glossary (+ the _*.html page-kind skeletons)
    ├── assets/                         style.css · app.js · site.json → site.js · glossary.json → glossary.js · data.js (built from the pages)
    └── tmp/                            git-ignored working files:
        ├── INSIGHTS.md                 stage 1 — detailed refined insight, derived policies, gaps, interview log
        ├── FIELD_MAP.md                field-scout output
        ├── BRIEF.md                    stage 2 — the research brief every agent builds against
        ├── BRIEF_REVIEW.md             brief-reviewer output
        ├── dossier/
        │   ├── 00-overview.md          dossier-consolidator output (incl. per-page build specs)
        │   ├── mNN-<slug>.md           one per module (module-researcher; source-verifier edits the Verified column)
        │   ├── sNN-<slug>.md           one per synthesis part (project, stacks, matrices, questions, roadmap)
        │   └── <name>.links.md         check_links.py report, one per dossier file (source-verifier)
        ├── SITE_PLAN.md                stage 4 — pages, writer assignments, conventions
        ├── SITE_REVIEW.md              site-reviewer output
        └── site/                       Format single only: the editable source of the page (index.html + assets/)
```

**Format single** changes only the built output: the topic folder holds `PLAN.md`, `topic.json`, `index.html` (the self-contained page that `bundle.py` generates from `tmp/site/`) and `tmp/`. There is no `pages/` or `assets/` at the topic root.

`tmp/` is git-ignored (`topics/*/tmp/`) but the plugin never clears it: a resume on the same machine finds everything. A fresh clone cannot resume a half-finished research; the built site, `PLAN.md` and `topic.json` are the durable record. A second run with an existing slug asks before overwriting anything.

Only the main agent writes `PLAN.md`, `topic.json` and `tmp/SITE_PLAN.md`. Agents write exactly the files their dispatch names. Scripts never write the plan; `build_index.py` writes only the three root files.

Paths in this document are relative to the topic folder unless they start with `<repo>` or `<PLUGIN_ROOT>`.

## 3. The plan — `topics/<slug>/PLAN.md`

Short (target ≤ 60 lines), simple words except terminology, written for a human catching up. Details stay in `tmp/`. Template: `references/plan-template.md`. Shape (every line below is checked by `check_plan.py`):

```markdown
# Research plan: <Title>

**Slug**: <slug>
**Folder**: topics/<slug>/
**Stage**: insights | brief | research | compose | done
**Format**: site | single
**Updated**: YYYY-MM-DD

## What I want
- **Goal**: <one sentence>
- **Why**: <one sentence>
- **Use**: <one sentence>
- **Start**: <one sentence — what I already know or have>
- **Focus**: <one or two sentences — priority angles, must-answer questions, anchor example>
- **Skip**: <one sentence>
- **Done when**: <one sentence>
- **How**: depth <overview|textbook|monograph|mixed> · verify <strict|standard|light> · demos <rich|moderate|minimal> · media <…> · <language, units>

Details: `tmp/INSIGHTS.md`

## Progress
| Status | Stage | Output |
|---|---|---|
| [ ] | insights | tmp/INSIGHTS.md |
| [ ] | brief | tmp/BRIEF.md |
| [ ] | research | tmp/dossier/ |
| [ ] | compose | index.html |

## Modules
| # | Module | Researched | Checked | Page |
|---|---|---|---|---|
| M01 | <title> | [ ] | [ ] | [ ] |
| S01 | <synthesis part> | [ ] | [SKIP] | [ ] |

## Next
<one line: the command to run and what it will do>

## Notes
- Changed 1 (research, 2026-11-05): M07 skipped — no verifiable sources at standard level.
- Caveat 1 (research, 2026-11-05): 3 references unverified; listed in tmp/dossier/00-overview.md.
- Lesson 1 (research, 2026-11-05): researcher prompt lacked the running-example path.
```

Rules:
- `**Format**` is optional (missing = `site`). It is not part of `## What I want`, so changing it does not change the insight hash. Every change after stage 1 gets a `Changed` note.
- `**Readers**` (I1) and `**Discovery**` (I5) are optional header lines copied from the INSIGHTS.md rows of the same names, outside the hash like `**Format**`. `check_plan.py` fails an unknown persona (`Readers persona \`x\` is not one of: …`) or class (`Discovery class \`x\` is not one of: none, …`), warns on more than two personas, and warns when the header differs from its INSIGHTS.md row.
- `**Slug**` equals the folder name; `**Folder**` is `topics/<slug>/`. `tmp/` and the site are resolved from the plan's own location, never from the text.
- Markers are exactly `[ ]`, `[x]`, `[SKIP]`. Stages are sequential: no `[x]` after a `[ ]` in Progress; a `[SKIP]` counts as closed. `**Stage**` equals the first Progress row that is `[ ]` (`done` when none is).
- Module ids `M01…` for modules, `S01…` for synthesis parts, ascending, never renumbered. `Checked` is `[SKIP]` when verification is `light` or the row is a synthesis part — these two cases need no note; every other `[SKIP]` has a `Changed` note that names the id.
- `## Modules` is empty until the brief is approved; then it mirrors the brief's module headings (id + title).
- `## Notes` is append-only. Three kinds, numbered per kind: `Changed n` (a deviation from the brief or a skipped item), `Caveat n` (what the reader of the site must know: unverified items, hedged numbers, gaps), `Lesson n` (a prompt-file problem reported in an agent's `Friction:` line). One sentence each; the detail is in `tmp/`.
- `## What I want` is transcribed by the main agent from `tmp/INSIGHTS.md` after the refiner's pass, one sentence per key; the `How` line is the policies table in one line.
- No `{placeholder}` text may remain. More than 120 lines is a warning: move detail to `tmp/`.

## 4. INSIGHTS.md

Template: `skills/collect-insights/references/insights-template.md`. Header: `# Insights: <Title>`, then `**Slug**`, `**Status**: Draft | Confirmed`, `**Updated**`, `**Rounds**`. Sections, in order:

1. `## Refined insight` with `### Goal`, `### Why`, `### Use`, `### Start`, `### Focus`, `### Skip`, `### Done when` — paragraphs, detailed, in the user's own terms made precise.
2. `## How (derived policies)` — table `| Policy | Value | Because |` with rows Document type, Format, Depth, Verify, Freshness, Demos, Media, Language, Region. Set by the refiner from the insight; the user may change any row before brief approval. The Format row records the first derivation; the plan header carries the live value.
3. `## Open gaps` — table `| # | Question | Blocking | Status |`, ids `G-01…`, Status ∈ `open | asked | answered | you-decide`.
4. `## Interview log` — append-only, one `### Round n — YYYY-MM-DD` block per round; per question: `**Q (dimension)**:`, `Options:`, `**A**:`.

**I4 derived policies** — the `## How (derived policies)` table also carries the rows `Must cite` (seed sources the researchers search first: named textbooks, standards, documentation roots, from Starting point and Boundaries; `none`), `Must avoid` (sources never cited, from Boundaries; `none`), `Citation style` (`numeric` | `author-year`), `Licence` (the output's licence; default `all rights reserved, personal use`; `CC BY 4.0` when Use is teaching) and `Accessibility` (`none` | `large text` | `dyslexia` | `screen reader` | `reduced motion`, from anything the user says about reading). The refiner sets them; the brief copies them (§5) and the compose stage turns Licence and Accessibility into the SITE_PLAN `**Licence**` / `**A11y**` header lines (§7).

**I1 reader emphasis / I5 discovery** — two more rows, both derived, never asked: `Readers` (one or two of `creative student | engineer | software developer | circuit designer | researcher | fundamental sciences | instructor | accessibility/mobile`, from the Use and Goal answers, Because = the user's words quoted; default `creative student`) and `Discovery` (`none` by default, or any of `datasets | code | standards | lectures`, from Use, Goal and Readers). An ambiguous Readers derivation produces at most one non-blocking `you-decide` gap, never a question. The brief copies both into its appendix (§1 `Reader emphasis`, §2.1 `Discovery`); the brief author leans the modules on the persona's emphasis, the researchers spend at most 2 extra searches per module per discovery class, and the compose stage adds catalog modules per persona (`skills/compose/SKILL.md` §1). Both rows are optional for the gates.

The **insight hash** = first 12 hex characters of SHA-256 over the normalised text (heading lines excluded; lines trimmed, runs of spaces collapsed, blank lines dropped) of: the plan's `## What I want` section + `INSIGHTS.md` `## Refined insight` + `## How (derived policies)` sections, in that order. `check_plan.py --hash` prints it as `HASH: <12hex>`. `BRIEF.md` carries it; a mismatch before research fails the gate.

## 5. BRIEF.md

Template: `skills/research/references/brief-template.md`. Header lines: `# Research brief: <Title>`, `**Slug**`, `**Status**: Draft | Approved`, `**Insight hash**: <12 hex>`, `**Updated**`. Sections: §1 research mission · §2 methodology and source policy (2.1 sources, 2.2 verification, 2.3 presentation) · §3 modules · §4 synthesis parts · §5 must-answer questions · §6 out of scope · §7 anchor example · §8 quality requirements (fixed text) · §9 interactive report requirements (fixed text) · §10 success test · §11 final deliverables · §12 research allocation · appendix: derived policies.

A **single**-format brief has the same shape with fewer, tighter modules: 2–6 parts in total, 5–15 topics each, §9 in its single-page variant (template), scale line "n parts on one page". `estimate_size.py` estimates the page from it.

**I2 learning design** — `## 13. Learning design` sits between §12 and the appendix. It is filled only when the Document type is a textbook curriculum or the Use is teaching (otherwise the one line `n/a — <why>`): per module the outcomes with Bloom verbs (`O1 (apply): …`), the assessment plan (one row per outcome: checkpoint / exercise / deliverable), the course alignment (sessions or weeks; `Hours` per module, which the compose stage copies into the SITE_PLAN Pages table's `Hours` column) and the prerequisites between modules. **I4** — the appendix carries the five policy rows of §4; §2.1 lists the must-cite sources first and the must-avoid sources as excluded; §2.3 names the citation style.

Module headings exactly `### M01 — <Title>` (in §3) and `### S01 — <Title>` (in §4); the plan's `## Modules` rows are transcribed from these headings. Each module section carries a `Level: <1–4> · Group: <group> · Priority: yes|no` line (exactly one `yes`), purpose, an exhaustive topic list, running-example instance, interactive candidates, media, deliverable.

## 6. Dossier files

Template: `skills/research/references/dossier-template.md`. One file per module (`mNN-<slug>.md`) or synthesis part (`sNN-<slug>.md`), named `<id lowercase>-<title slug>.md`. `check_dossier.py` enforces: every row in `## Sources` has a `http(s)` link, a Tier ∈ {1,2,3} and a Status ∈ {foundational, established, recent, experimental, discontinued, preprint}; the Verified column is never blank and never says `model knowledge`; every row in `## Key facts and numbers` cites a source number that exists and a `Locator` (section, page, table, equation, or `whole page`); every row in `## Documented calculations` (ids `C1…`: formula or algorithm as the source writes it, inputs, output, validity, source #, locator) and `## Documented relationships` (ids `R1…`: from, relation, to, source #, locator) cites an existing source and a locator; `## Running-example parameters` rows cite a source number or `user` (a user-provided value); `estimate` is accepted nowhere; every `## Interactive demo candidates` item names the `C` id it implements; every row in `## Media candidates` has a licence; every section of the template is present (a section with nothing to say contains `none`). Evidence policy §2–§6.

Verified-column vocabulary: `Crossref ✓` · `arXiv ✓` · `OpenLibrary ✓` · `oEmbed ✓` · `Commons ✓` · `fetched ✓` · `not confirmed automatically — <why>` · `✗ dead link` · `✗ mismatch: <what differs>`. A reference nobody retrieved is not a source row: it goes to `## Could not verify` with an evidence label (`Not specified` · `Insufficient evidence` · `Not available in sources`, evidence policy §3).

**I5 source kind** — the Sources table (and the overview's bibliography seed) may carry a `Kind` column: `paper | dataset | code | standard | lecture | book | web`. `check_dossier.py` fails an unknown kind (`Kind \`x\` must be one of …`), warns on a blank one, and adds `kinds=paper:n,…` to its RESULT line. `enrich_openalex.py` appends `## OpenAlex enrichment` with one `- Enriched: #n — doi:… · year · venue · type · cited by n · OA <url>|no OA copy · not retracted|RETRACTED (OpenAlex, date)` line per source with a DOI or arXiv id; nobody else edits that section.

`source-verifier` edits only the Verified column (and empty Author/Licence/Artist cells of media rows), adds lines under `## Could not verify` when verification is strict, and appends `## Verification log`.

`dossier/00-overview.md` (template block in `dossier-template.md`) has sections `## 1. Running-example parameter sheet` … `## 8. Build notes`: parameter sheet, overlaps and ownership, glossary seed, bibliography seed, media list, conflicts and limitations, unverified items, build notes. **Build notes** contain `**Groups**`, `**Levels**`, `**Priority module**` lines and one `### Page <file>.html — <Title> (<id>, level <n>, <size target>)` block per page of the future site — modules, synthesis parts, `index.html`, `bibliography.html`, `glossary.html` — each with `- Topics`, `- Diagrams`, `- Tables`, `- Demos`, `- Sources`, `- Media`, `- Cross-links`, `- Numbers` lines (`n/a` where a line does not apply; `level —` for pages without a level). These blocks are the page specs the writers receive. `check_dossier.py --overview` fails a `- Demos:` line that names no documented calculation (`m04 C2`), a `- Diagrams:` line that cites no documented relationship or source (`m04 R3`, `m04 #7`) and a §1 parameter without a source or `user`; a page with no evidence of that shape says `none — <why>` (evidence policy §7.6).

## 7. SITE_PLAN.md

Written by the main agent in stage 4 from the brief and the build notes. Header: `# Site plan: <Title>`, `**Slug**`, `**Title**`, `**Subtitle**`, `**Prefix**` (storage prefix = slug), optional `**Format**: single` with `**Budget**: 250 KB` (single page: `scaffold.py` writes `mode: single` and `budgetKb` into `site.json`), `**Pages dir**: pages/` (the default; `flat` keeps every page at the site root; always `flat` for single), `**Levels**: 1 <name> · 2 <name> · …`, `**Footnote**: <one sentence>`, `**Status**: Draft | Built`. Sections:

1. `## Pages` — table `| File | Num | Title | Group | Level | Desc | Spec | Writer | Size | Status |`; File is the basename (`index.html`, `m01-slug.html` …); Level empty for pages without a level; Spec = `00-overview.md#page-<file>` or `brief`; Writer = `W0` (index, written last), `W1…`; Status marker. `scaffold.py --plan` turns this table and the header into `assets/site.json`.
2. `## Writers` — one `### W1 — <pages>` block per writer with the exact dispatch text (page specs copied from the build notes, interactive requirements, cross-links, numbers, size targets) and one line per page `- <file> — Kind: module|synthesis|reference|index · Modules: <catalog module ids>` (derivation table in the compose skill §1).
3. `## Conventions` — frames, units, symbols, naming, running-example numbers every page must use.

**F3 bilingual glossary (nav)** — an optional header line `**Second language**: Vietnamese` becomes `site.json` `secondLanguage` (scaffold.py); the glossary owner then fills `term_local` / `def_local` in `glossary.json`.

**E6 version / F4 hours** — the header may carry `**Version**: 1.0` (→ `site.json version`, shown in every page's footer stamp and on `changelog.html`; bumped at every stage close) and the Pages table an optional `Hours` column (`25` or `20–30` → `pages[].hours`, the midpoint of a range; the study planner's input; a value that is neither fails the scaffold with `Hours \`x\` must be a number or a range like \`20–30\``).

**I4 derived policies** — two optional header lines, written from the INSIGHTS.md policies: `**Licence**: <text>` (e.g. `CC BY-SA 4.0`; `none` omits it) → `site.json` `licence`; `**A11y**: font dyslexic · scale 1.15 · motion reduced · contrast high` (any subset, any order; `font default|dyslexic`, `scale 1|1.15|1.3`, `motion normal|reduced`, `contrast normal|high`) → `site.json` `a11y`. `scaffold.py` fails on a value outside these sets.

## 8. Site layout and registry

Layout: `index.html` at the site root (= the topic folder); every other page in `pagesDir` (`pages/`); `assets/` at the site root. **Page kinds**: `pages/_module.html`, `pages/_synthesis.html`, `pages/_reference.html` are the skeletons writers copy (required sections stubbed in order, trust footer last); `pages/_skeleton.html` is the bare frame; `_*.html` files are never registered and the validator skips them. Registry `file` values and `data-page` are basenames. Pages under `pagesDir` include `../assets/…`; `index.html` includes `assets/…`. Cross-links between pages are `other-page.html#id`; a page links to the overview as `../index.html`; the overview links to `pages/<file>`. `app.js` builds every navigation link from a root prefix it computes from its own location.

`assets/site.json` is the registry source of truth; `assets/site.js` (`window.SITE = …;`) is generated from it by `scaffold.py` and read by the fixed `app.js`. `assets/glossary.json` (array of `{term, aka?, def, page, anchor?}`) is the glossary source; `assets/glossary.js` (`window.QC_GLOSSARY = …;`) is generated. Edit the JSON, run `python <PLUGIN_ROOT>/scripts/scaffold.py <site> --sync`. `validate.py` fails when a `.js` is out of sync with its `.json`.

`assets/data.js` (`window.QC_DATA = {…};`) is **built from the pages** by `build_site_data.py` (run by `scaffold.py --sync` and once more by the compose skill before the final validation): one key per builder — indexes, backlinks, evidence, manifest, notation, concepts, changelog, planner — every key optional, so the runtime renders what is there. Every page includes it after `glossary.js`; `scaffold.py --plan` writes an empty stub so the include resolves before the pages exist. The template's reference pages `indexes.html`, `notation.html`, `concepts.html` and `changelog.html` render from it; `scaffold.py` copies them beside `glossary.html` and registers them under the `Reference` group when the site plan does not list them (site format only; a single page may embed the same widgets).

**sitewide (A1 A3 E5 G4 H6)** — `data.js` keys `indexes` (figures, tables, equations, code listings, concepts A–Z), `backlinks` (`"page.html#id"` → the pages and sections that link there), `evidence` (per page the claims `span.claim[data-src]` and bare `a.cite` with their sources, plus site-wide citation totals) and `manifest` (the site manifest without section text). `build_site_data.py` also writes `assets/manifest.json` (the manifest with the plain text of every section, for search, RAG or a hosted tutor) and `assets/media.json` (every photo, compare and embed figure with credit, credit URL and the licence parsed from the credit). `pages/indexes.html` (template page, registered as `IX` under Reference) renders `DATA.indexes` in `div.indexes[data-indexes]`. `validate.py` fails a `span.claim` whose `data-src` does not resolve, warns about media without a licence and about an `assets/data.js` older than the newest page, and adds `claims=n` to its RESULT line. Shapes: `skills/compose/components/sitewide/README.md`.

**C12 / E6 / F4 data (pages)** — `assets/changelog.json` is optional: `[{ "date": "YYYY-MM-DD", "version": "1.0", "note": "…", "pages": ["m01-….html"] }]`, one entry appended by the compose skill at every stage close → `DATA.changelog = { version, entries }` (entries sorted by date, newest first; `version` = `site.json version`, else the newest entry's). Glossary entries may carry `related: ["Term", …]` (names of other terms or their akas) → `DATA.concepts = { nodes: [{ id: "gl-<slug>", term, page, anchor, group }], edges: [{ a, b, kind: "related" | "mentions" }] }` (ids follow the inline glossary widget's `gl-<slug>` rule; a mention is another term's name found in a definition, ≥ 4 letters, ≤ 8 per term). `DATA.planner = { pages: [{ file, title, num, hours }] }` lists every module and every page with `hours` (from the registry, else the midpoint of the module hero's `Study time ≈ 20–30 h`, else `null`). `site.json` may carry `version` and `licence` (strings); the runtime appends `p.site-stamp` (version · date · `Text: <licence>` · changelog link) to every module footer and a *last change* pill to the trust footer of a page an entry names. Template pages `concepts.html` (num `CM`, `svg[data-concept-map]`) and `changelog.html` (num `CL`, `div.changelog[data-changelog]`) render from these keys; `div.planner[data-planner]` is the study planner widget (any page).

**E3 notation (scholar)** — `assets/notation.json` is optional, hand-written beside `glossary.json`: an array of `{ "symbol": "λ", "tex": "\\lambda", "meaning": "longitude", "unit": "rad", "kind": "symbol"|"constant", "value": "…", "page": "m01-….html", "anchor": "…" }` (`symbol` and `meaning` required). `build_site_data.py` merges it with every `table.notation` / `table.constants` row of the pages into `DATA.notation = { entries: [...], pages: n }` (entry keys `symbol tex meaning unit kind value page anchor where`); `template/notation.html` (registry num `N`, group `Reference`, copied and registered by `scaffold.py` like the other reference pages) renders it through `div.notation-page[data-notation]`, and every entry joins the site search. `validate.py` checks the file's shape and warns when one symbol has two meanings across the site.

`site.json`:
```json
{
  "title": "…", "subtitle": "Interactive Research Report", "storagePrefix": "<slug>", "home": "index.html",
  "pagesDir": "pages/",
  "searchPlaceholder": "Search modules, sections & terms  ( / )",
  "levels": { "1": "Foundations", "2": "Practical engineering", "3": "Advanced topics", "4": "Research frontier" },
  "footnote": "…",
  "theme": { "accent": "#0b5cad", "accentSoft": "#e2ecf8", "dark": { "accent": "#6aa8ff", "accentSoft": "#16263d" } },
  "pages": [ { "file": "index.html", "num": "00", "title": "…", "group": "Overview", "desc": "…" },
             { "file": "m01-slug.html", "num": "01", "title": "…", "group": "Foundations", "level": 1, "desc": "…" } ]
}
```

**Single page** (`"mode": "single"`, `"pagesDir": ""`, `"budgetKb": 250`, exactly one registry entry: `index.html`, group `Guide`, no level). The source site is `tmp/site/` (flat: `index.html`, `_single.html`, `assets/`); the writer copies `_single.html`. Page shape, in order: hero (`module-hero home-hero`, eyebrow "Single-page guide · …", meta strip with reading time, level, parts, deliverable) · `#summary` (objectives + key-takeaway cards) · optional `#map` · one `section.part[data-part="M01"]` per brief module or synthesis part, each with an `h2` id like `m01-<slug>` and a `p.part-more` pointing to the references · `#checkpoints` · optional `#exercises` · `#glossary` (`div.glossary-inline[data-glossary]`, rendered from `glossary.js`) · `#references` (all `ol.refs` entries in one list) · `section.trust` last. ## 11. Dispatch protocol (main agent)

1. Fill a dispatch from paths and policies only — never paste content. **Label every value with the input name the agent's role file lists** (`PLAN:`, `BRIEF:`, `OUT:`, `HOW:`, `MODE:`, `PAGE_KIND:`, `MODULES:`, `CATALOG:` …), one per line, absolute paths. Always include `SLUG`, `DATE`, `PLUGIN_ROOT` and the line `End with Friction lines and the RESULT line (contracts §10).` Every agent that writes or judges content (scout, refiner, brief author and reviewer, researcher, verifier, consolidator, writer, site reviewer) reads `<PLUGIN_ROOT>/references/evidence-policy.md` before it works; dispatches may name it as `POLICY:`. Writers and the reviewer get `CATALOG` and the `MODULES` of their pages so they load only those modules; a writer's `Friction:` line naming an unlisted module is a `Lesson` for the derivation table.
2. Launch a wave's agents in **one message** (researchers ≤ 5 per wave, verifiers ≤ 8, writers ≤ 6). The priority module gets its own agent.
3. On each report: parse the `RESULT:` line; if `files=` names nothing, do not flip anything; run the gate on each named file; flip the row only when the gate passed.
4. Retry rule: one retry, narrowed to the failing items and carrying the gate's error lines verbatim; on a second failure mark `[SKIP]` with a `Changed` note and continue. Never take the work over yourself.
5. Append every `Friction:` line as a `Lesson` note; append `Caveat` notes from `unverified=`, `gaps=` and the reviewer's caveats.
6. Ask the user only at gates: the interview, brief approval, a stage that failed twice, overwriting an existing slug. Use `AskUserQuestion`, recommended option first.
7. Update `**Stage**`, `**Updated**` and `## Next` after every flip; update `topic.json` (`status`, `updated`, `pages`) and run `build_index.py` when a stage closes; run `check_plan.py` before ending the turn.
8. Never read a dossier file or a page in full; read RESULT lines, gate output, review verdict tables and the 6-line summaries the skills ask for.

## 12. PLUGIN_ROOT

Skills refer to the plugin folder as `${CLAUDE_PLUGIN_ROOT}`. If that text appears unsubstituted, the main agent resolves it once with Glob (`**/plugins/atlas-learn/.claude-plugin/plugin.json`) and passes the absolute folder to every script call and dispatch as `PLUGIN_ROOT`.

## 13. Topic metadata and the dictionary

`topics/<slug>/topic.json` — written by the main agent at the end of stage 1, updated at every stage close. It is the only thing the dictionary knows about a topic; the topic's content is never read by the dictionary or by `build_index.py`.

```json
{
  "code": "map-projections",
  "name": "How map projections work",
  "description": "One sentence a stranger can understand.",
  "tags": ["cartography", "geodesy", "gis"],
  "status": "research",
  "created": "2026-11-05",
  "updated": "2026-11-07",
  "pages": 0,
  "entry": "index.html",
  "format": "site"
}
```

Rules: `format` is optional (`site` | `single`, copied from the plan header; the dictionary shows a "single page" chip); `code` = the folder name = the plan's slug; `name` = the plan's title; `description` ≤ 160 characters, plain words; `tags` 1–8 lowercase kebab-case strings (field-map themes + the user's own words); `status` ∈ `insights | brief | research | compose | done`; dates `YYYY-MM-DD`; `pages` = number of `.html` pages in the site (0 until compose); `entry` = the site's overview page relative to the topic folder.

`<repo>/index.html`: the dictionary page from `<PLUGIN_ROOT>/templates/root-index.html` — one self-contained file (inline CSS and JS, system fonts, no libraries, no reference to any topic's assets, no sidecar data file) with a text filter over name, description and tags, tag and status chips, sort by updated or name, and one card per topic linking to `topics/<code>/<entry>`. Its data — `{ "generated": "<ISO timestamp>", "topics": [ …topic.json objects…, sorted by updated desc ] }` — is embedded inline in the `topics-data` JSON block, which is the only place the data lives.
