# Authoring rules (atlas-learn compose)

These rules apply to every page written by an `atlas-learn:page-writer`. The component catalog (`../components/`, `INDEX.md` + one folder per module with a `README.md` and copy-ready snippets) says *how* to mark things up and is loaded module by module as the dispatch's `MODULES` line says; this file says *what* a page must contain and how claims must be supported. Above both sits `references/evidence-policy.md` (in the plugin root): read it first. In one line — **an interactive visualization of what the dossier documents, every element traced to its source, nothing the dossier does not establish, every gap visible.**

## 1. Module page structure (learning modules — pages with a `level`)

In this order (the `_module.html` skeleton carries it); headings may be reworded, ids must exist:

1. `#objectives` — `ol.objectives`, 4–8 items, each a capability ("derive…", "size…", "choose…"), plus `.keywords`.
2. `#introduction` (or `#intro`) — conceptual introduction: what, why, where it sits in the system; one diagram or photo if it helps.
3. Technical sections — one `h2` per topic group of the brief, `h3` per sub-topic. **Cover every listed topic** from the dossier; if a topic is too large, give a technically meaningful overview + keywords + reading direction rather than skipping it — still cited. A topic the dossier does not document is named, marked `badge unavailable` and listed as a gap, never written from memory. **Lead each section with the visualization its evidence supports** (§4a), then the prose that explains it.
4. Mathematical formulation — `.math5` blocks for each key equation set the dossier documents, cited; derivations in `<details>` when long and only as far as the source derives.
5. Architecture / flow diagrams — `figure.diagram` SVG with legend; data, control and power paths distinguished; every box and every path is a documented component or relationship (the dossier's `R` rows) and carries `data-cite` (§4a).
6. Practical hardware/tool examples — named products or tools from the dossier, with its official links, its date and its status badges.
7. Implementation examples — code blocks (`tabs` for multi-language), commented; an API, parameter or behaviour shown in code is one the dossier documents.
8. Running-example case study — `.callout.case` applying the module to the reference platform with the parameter-sheet numbers; every derived number computed by a documented calculation (§3a); a user-provided value labelled `user-input`.
9. Comparison tables — interactive `.table-wrap` when ≥ 5 rows; one cited row per item; an empty cell is `—` with `badge not-specified`, never a guess.
10. `#mistakes` — the mistakes and pitfalls the sources describe (`.callout.mistakes` or list), each with the symptom and the fix, cited.
11. `#reading` — `ol.refs`, 6–15 entries with a "why read it" note and status badge.
12. `#checkpoints` — 3–6 `.quiz` blocks.
13. `#exercises` — 2–4 `.exercise` blocks (problem with the numbers to use, hints revealed one by one, a closed solution that actually solves it); the brief's success test may raise or drop the count.
14. `#deliverable` — the module deliverable named in the brief, clearly marked and self-contained (diagram, table, code, plan or calculator).
15. `section.trust` — the trust footer, always the last section: `data-reviewed` = the run date, the assumptions the page's demos and numbers rest on, the page's open gaps (same lines as the `## Gaps` list in the report; omit the block when there are none). `app.js` fills the counts (sources verified, demos, gaps) from the page itself.

Synthesis and reference pages (no `level`) keep `#objectives`-style intro, diagrams, tables, references and checkpoints where useful, but follow the structure their brief section implies (project stages, stacks, matrices, research questions, roadmap, bibliography) on `_synthesis.html` / `_reference.html`; they end with the trust footer too. Only `index.html` and `glossary.html` have none.

**Single page** (Format single, `_single.html`): hero · `#summary` · optional `#map` · one `section.part[data-part]` per module or synthesis part · `#checkpoints` · optional `#exercises` · `#glossary` · `#references` · trust footer. Each part is the module condensed: every topic named at least once, one key equation set, one diagram, one worked example, the pitfalls, a pointer to the references. The whole page stays within about 250 KB (see `components/single/README.md`).

Depth target: textbook, not overview. Typical module page 70–160 KB of HTML; the brief's priority module may reach 250 KB. Use `<details>` so pages stay scannable.

- **F4 study time** — keep the hero's `Study time` value a number or a range in hours (`≈ 20–30 h`, `8 h`): the study planner reads it when the site plan's Pages table has no `Hours` column; a module without either is listed but not scheduled.

## 2. Writing style

- Audience: a motivated engineer or student progressing from beginner to researcher. Precise, consistent terminology; define conventions explicitly (frames, units, sign conventions, naming) the first time and keep them for the whole site — `SITE_PLAN.md` → `## Conventions` is binding.
- Tie theory to real hardware/tools; use the running example consistently, but **distinguish general principles from example-specific choices**, and compare alternatives.
- Separate what is deterministic/critical from what is best-effort (e.g. real-time MCU loop vs companion computer; production vs research code).
- Prefer tables for comparisons, diagrams for structure and flow, demos for parameter intuition, prose for reasoning. Do not restate a table in prose.
- Mark evidence status with badges: established practice vs experimental research vs emerging/discontinued products. Note conflicting findings and limitations explicitly (the dossier's "Conflicts" sections); do not treat the newest technology as automatically better.
- Safety and legal considerations appear wherever the reader could act on the content (`.callout.safety`); technical capability ≠ legal permission.
- Numbers: every number is cited to its dossier source (or is the reader's own input in a demo, or a value computed in front of the reader by a cited method). "Typical", "usually" and ranges appear only when the source says them; prices only with the source's date and "varies by vendor" when the source says so. A value the dossier lacks is a gap with a visible badge, never a "typical" figure. The running-example numbers come from `dossier/00-overview.md` §1 and are the same on every page; a `user` value there is shown with `badge user-input`.
- **About the subject, never about the making (evidence policy §10).** Write only what the sources say about the subject. No sentence explains what you, an agent or the workflow did or why ("this diagram was added to…", "we chose…", "there is no demo because…", "the researcher could not find…"), and the page never names the dossier, the brief, the site plan, page blocks, build notes or any agent role — cite the source itself. A gap reads as a statement about the sources ("The datasheet does not state X" + badge). Reasons go in your report, not on the page; the validator fails process text.
- Short paragraphs, ≤ 6 sentences per paragraph.
- **H3 glossary links** — do not link glossary terms by hand: the runtime turns the first occurrence of each glossary term in every `h2` section into a tooltip with its definition and a link to the glossary. Mark the one place a term is *defined* with `<dfn>` (that section gets no automatic link for it). Wrap text that must stay untouched (a quotation, a product name that happens to be a term) in `<span class="no-gloss">`; a page that should get no links at all carries `data-no-glossary-links` on `<main>`.
- **A2 section metadata** — when a section needs another one first, say it on the `h2`, not in prose: `data-prereq="m01-globe.html#scale"` (and `data-related` for sections that pair with it); the runtime renders the chips with the target's title. Use `data-time` only when the automatic estimate misleads (a section that is mostly code or tables) and `data-reviewed` only for a section checked on a date other than the page's trust footer. One or two sections per page, not all of them (`components/core/section-meta.html`).

## 3. Accuracy and references (non-negotiable)

- **The dossier is the only source.** Cite only works, URLs, numbers, media and product facts that appear in your dossier files (`dossier/mNN-….md`) or in `dossier/00-overview.md` with a verified mark. Writers have no web access and do not search.
- **Never fabricate** papers, authors, years, DOIs, URLs, datasheet numbers, part numbers, prices, dates, regulations or results — and never add an item from memory because the dossier lacks it.
- **A needed fact the dossier does not have is a gap.** Leave `<!-- GAP: what is missing -->` at the spot **and** a visible badge beside the affected text — `<span class="badge unavailable">Not available in sources</span>` (no source covers it), `badge not-specified` (the source covers the subject but not this value) or `badge insufficient` (too little to state it) — write the section honestly around it, list it under `## Gaps` in your report as `page#section: what is missing`, and set `gaps=` in your `RESULT:` line. The validator fails a page with more GAP markers than visible gap badges. The main agent sends a researcher; you will be asked to fill the section afterwards.
- Items marked `✗` or `not confirmed automatically` in the dossier, and anything under `## Could not verify`, are not cited as facts; mention them only as "reported, unverified" leads under `#reading` with the badge `experimental` or `neutral`, or leave them out.

### 3a. Calculations, inference and user input (evidence policy §2, §5, §6)

- **Compute only documented calculations.** A formula or algorithm on the page — in prose, `.math5`, a worked example, an exercise solution, a demo or a plot — is one the dossier lists under `## Documented calculations` (or states as a key fact), and it is cited. Its inputs are documented values, the parameter sheet's values, the exercise's stated inputs or the reader's own. Never derive a new formula, chain two documented ones into a result no source gives, extrapolate past the documented validity range, or fill a missing input with a remembered value: write what is missing with a badge and report the gap.
- **Infer nothing.** A cause, comparison, ranking, trend, dependency or "therefore" appears only when a source states it. A hypothesis or open question is labelled (`callout research`, `badge experimental`) and cited to whoever proposed it.
- **User-provided is not sourced.** A value or statement from the user (the parameter sheet's `user` rows) carries `badge user-input`; when a source disagrees, both are shown with `badge conflict`.
- **Conflicts are shown, not settled.** Both values, both cites, `badge conflict`, in the way §6 of the overview says; a worked example that must use one value says it is a choice.
- Prefer stable links as the dossier gives them: `https://doi.org/<DOI>`, `https://arxiv.org/abs/<id>`, official documentation roots, vendor product pages. Never "improve" a link into a deeper URL you have not seen.
- Reference entry = authors (surname initials), year, linked title, venue, status badge, one-sentence "why read it" (the dossier's "Why worth studying" column), plus `<span class="badge verified">Verified</span>` when the dossier's Verified column says `✓` for that row — and only then. The trust footer counts these badges; a verified badge on an unverified source is a false claim.
- Images and embeds are references too: use the exact URL, attribution and licence from the dossier's media tables.
- **I4 citation style** — the brief's §2.3 names the citation style from the derived policies: `numeric` → the `a.cite` text is `[n]` in the order of the page's `ol.refs`; `author-year` → `(Surname Year)`; one style on every page of the site. Sources the brief lists under must-avoid are never cited, not even as "reported".
- When sources conflict, say so and give both values with sources.
- Date-stamp anything that changes (software versions, product status, regulations): "as of <month year>", from the dossier's freshness notes.
- **E5 claims** — wrap each number or fact you cite in `<span class="claim" data-src="#ref-key">…</span>` (the id of the `ol.refs` entry it rests on, or `other-page.html#ref-key`; the cite link may sit inside the span). The trust footer's evidence table and the site manifest are built from these spans; a `data-src` that does not resolve fails the page (`claim cites missing source #ref-key`).
- **C12 related terms** — the glossary writer may add `"related": ["Term", …]` to an entry (names of other glossary terms or their akas, 1–5 per entry): they draw the solid lines of the concept map; mentions inside definitions are found automatically. Name only terms that exist — the validator warns otherwise.
- **E1 citation fields** — every `ol.refs` entry also carries the dossier row as data: `data-type` (article|book|web|dataset|standard|thesis|report|software), `data-authors` (`Surname, I.; Surname, I.`), `data-year`, `data-title`, `data-venue`, `data-doi` or `data-url`, optional `data-key`. The BibTeX/RIS export and the citation hover cards are built from them (fallback: the entry's text); the visible entry stays as above. Only what the dossier gives — never complete a DOI from memory.

## 4. Interactive content rules

### 4a. Visualization first, from the evidence (evidence policy §7)

- **Choose the form from the shape of the evidence**: documented relationships → an interactive diagram (`diagrams`, `protocol`, `circuit`); comparable properties → a filterable table; a documented formula with ≥ 2 inputs → a demo or declarative plot; published values → a plot of exactly those values; dated events → a timeline; physical parts → a photo with hotspots or an exploded view. The page block's `- Diagrams/Tables/Demos` lines name the `R` ids, source #s and `C` ids to build from.
- **Every element is evidence.** A box, edge, layer, row, point, bar or event exists only when the dossier documents it; nothing is drawn for decoration or to fill a slot. Missing data stays missing (a gap in a series, `—` in a cell, with a badge).
- **Cite on the figure.** `data-cite="#ref-a, #ref-b"` on the `figure` (the runtime adds a "Sources: [n]" line) and, where elements rest on different sources, `data-cite` on the element itself (`g`, `rect`, `path`, `tr`, `li`) — the reader hovers it to see the source and clicks to open it. A figure or demo that cites nothing fails the validator; so does a `data-cite` that does not resolve.
- **Interactions add no claims.** Steps, layers, filters, tooltips, presets and the sensitivity view reveal or recompute what is documented.
- **No suitable visualization** — a definition, a single fact, a contested claim: write cited text; where a reader would expect a visual, state what the sources do not document (with a gap badge), never why the visual is absent (evidence policy §10).

### 4b. Demos and computed figures

- Every demo implements a documented calculation (the page block's `C` id) and cites it in its `.demo-note` (or `data-cite` on the `.demo`); the note states what the method does not model, as the source states it. Its head badge `illustrative` reads "Model output": the readouts are computed from the reader's inputs, not measured. The `illustrative` badge appears nowhere else — the validator fails it on a stated number.
- Readouts with units, NaN/instability guards, bounded loops (≤ ~20 000 steps), no blocking computation on input events (debounce or cap). Default input values come from the parameter sheet; slider ranges stay inside the documented validity range.
- Persisted state (checklists, trackers) must work when storage is blocked.
- Visual encodings use the CSS variables (`--s1…--s6`, `--data/--ctrl/--power`) so dark mode and print work.
- **C9 download** — every `figure.diagram` can be saved as SVG/PNG by the reader: keep labels as SVG `<text>`, colours in `d-*` classes and give the figure an `id` (it becomes the file name); page scripts that offer a file call `QC.download(filename, text, mime)`.
- **D1 demo state and presets** — give every `.demo` an id (the runtime keeps its inputs in the URL hash `#<id>?k=v`, and presets, "Copy link" and the export file need it); a preset is `div.demo-presets > button[data-preset="name"][data-state="k=v&k2=v2"]` naming input ids of that demo, first child of `.demo-controls`; a predict-then-reveal block refers to these names.
- **D2/D6 export and sensitivity cost nothing** when the demo follows the shape: numeric `.r-val` readouts with their unit in the text, a synchronous model (no debounce — the sensitivity view and the export read the readouts right after each input event), plotted canvases through `QC.plot`.
- **D3 units** — write sliders in one base unit and declare it: `input[data-unit-group="length"][data-unit="km"]` (`min`/`max`/`step`/`value` in that unit; the reader's unit menu converts the display, the model always receives the base unit); a prefixed number field is `input[type=text][data-si]` (never `type=number`). Units outside the table in `components/demos/README.md` keep a plain `data-unit` label.
- **D4 tolerances** — `data-tol="5"` (percent) on the inputs that carry one, `QC.tolerancesOf` + `QC.mc` + `QC.tornado` in the handler, and the `.demo-note` says which distribution the band means and that the seeded run is repeatable; never present a Monte Carlo spread as a measured uncertainty.
- **C5–C7 plots** (`components/plots/README.md`): label both axes with units and say in the caption what to notice; use a log axis (`xScale`/`yScale: 'log'`, `data-scale`) when the data spans more than two decades and never put zero or negative values on it; error bars state their meaning in the caption; a second axis is for a different quantity sharing the x values. Declarative figures (`figure.fnplot|field|sweep`) write their formulas in the safe expression language (numbers, `x`, the slider names, `pi`, `e`, `+ - * / ^ %`, the listed functions — not JavaScript), set `data-y` for functions with asymptotes, keep every slider as `name=min:max:step:value` and at most 24 sweep members; a computed figure plots a documented formula and says in its caption that it is computed, not measured; a data figure plots exactly the source's values — never interpolated, smoothed, averaged or extended; both cite their source (`data-cite`).
- **C2–C4 protocol diagrams** — a `figure.timing` / `figure.bitfield` holds strict JSON in one `<script type="application/json">`, a `figure.seq` / `figure.fsm` holds its text in one `<script type="text/plain">` (or a `<pre>`); write data, never coordinates or colours, never `</script` or `<!--` inside the script. Every `=`/`2`–`9` bus cell has a `data` label, field widths are whole numbers > 0 and fill the rows, every `loop`/`alt`/`opt` closes with `end`, a state machine starts with `[*] --> …`. Grammars: `components/protocol/README.md`.

## 5. Mechanics that break pages (checked by `scripts/validate.py`)

- `data-page` on `<body>` must equal the file name; the page must be registered in `assets/site.json` (the main agent owns the registry; `assets/site.js` is regenerated from it with `python <PLUGIN_ROOT>/scripts/scaffold.py <siteDir> --sync` — never edit `site.js` by hand).
- Inline math uses `\( … \)`; display `$$ … $$`. No `$$`/`$$$` as cost classes.
- Inside math in HTML: `<` → `&lt;`, `&` → `&amp;`.
- Unique ids; every `h2` has an id; cross-links target existing ids.
- No hard-coded colours inside SVG; no overlapping SVG labels (check coordinates).
- Quiz `data-answer` is a 0-based index within range.
- Every page under `pages/` except `glossary.html` ends with `section.trust` carrying a real `data-reviewed` date; nothing follows it.
- Every `.exercise` has an id and a `details.solution` that is **not** `open`; `data-difficulty` is 1–3.
- A `figure.diagram[data-steps]` has at least two `g[data-step]` layers and, when it lists `ol.diagram-steps`, exactly one caption per step.
- **C10 hotspots** — a `figure.photo[data-hotspots]` holds a `ul.hotspots`; every `li` carries numeric `data-x` and `data-y` in 0..100 (percent of the picture) and starts with a bold label.
- **C11 compare and layers** — a `figure.compare` holds exactly two panes of the same aspect ratio besides its caption and legend; a `figure.diagram[data-layers]` has at least two `g[data-layer]` groups with distinct, non-empty names.
- **B3 instructor notes** — `div.instructor` / `details.instructor` (and a `table.rubric` with a `thead`) are hidden from readers and from printed handouts: never put a fact the reader needs only there, never leave one empty, and keep every answer inside `details.solution`, `.quiz .explain` or `details.lab-answer` so handout mode can hide it.
- **B5 Bloom tags** — `data-bloom` is exactly one of `remember|understand|apply|analyze|evaluate|create`; `data-objective="1,3"` on a quiz, predict block, exercise or lab lists 1-based positions in the page's `ol.objectives`; a page with a `[data-outcomes]` matrix has that list (`data-outcomes="#id"` names it when the page has several); tag objectives when the brief has a learning design, otherwise leave them untagged.
- **B6 predict blocks** — `.predict` needs `data-demo` (the id of a `.demo` on the same page), a `data-preset` the demo defines and a 0-based `data-answer` within its options; place it directly above the demo.
- **B7 lab sheets** — `section.lab` needs an id, an `ol.steps`, a `ul.checklist[data-key]` with a site-unique key, and keeps expected results in a closed `details.lab-answer`.
- **C5–C7 plots**: a `figure.fnplot` has `data-fn` and a numeric `data-x="min,max"`, its `data-vars` entries are `name=min:max[:step[:value]]`; a `figure.field` has `data-fx` and `data-fy`; a `figure.sweep` has `data-fn`, `data-x` and `data-sweep="name=min:max:step"` with at most 24 members; every expression uses only the allowed characters, balanced parentheses and known names (`fnplot expression: unknown function "foo"` otherwise).
- Tags balanced; the page JavaScript parses — run `python <PLUGIN_ROOT>/scripts/validate.py <siteDir> --pages <your files>`; it checks inline-script syntax with `node` when node is present and says `js_syntax=skipped` otherwise.
- External `http(s)` links open in a new tab automatically; do not add `target` by hand.
- **A2 section metadata** — every `data-prereq` / `data-related` target on an `h2` is a real `page.html#id` (resolved from your page's folder like any link; `../index.html#id` for the overview); `data-reviewed` on an `h2` is a `YYYY-MM-DD` date; `data-prereq` on an `h3` is ignored (warning).
- **F3 bilingual glossary** — `term_local` / `def_local` in `glossary.json` are strings; when the site plan names a `**Second language**`, fill `term_local` for every term you add (the validator warns when the language is set but no entry has it).
- **B2 theorem blocks** — a result, definition, example or remark the text cites is `div.thm[data-kind][id="thm-…"]` (kinds theorem|lemma|proposition|corollary|definition|example|remark|proof, optional `span.thm-title`); numbering is the runtime's, never written by hand; a proof is its own `.thm[data-kind="proof"]` directly after the statement and contains no other block; cross-reference with an empty `<a class="thmref" href="#thm-…"></a>`.
- **E2 numbered equations** — a display equation the text refers back to is `div.eq[id="eq-…"]` (one `$$ … $$` inside); the runtime numbers them in page order and fills an empty `<a class="eqref" href="#eq-…"></a>` with "(n)"; `data-label` only to override a number; never type "(1)" by hand.
- **E3 notation** — a module that introduces symbols ends its conventions with one `table.notation` (Symbol | Meaning | Unit | Where defined; `td.sym` holds the symbol as inline maths) and lists the constants it relies on in a `table.constants` (Constant | Symbol | Value | Unit | Source); one symbol keeps one meaning across the whole site (the validator warns) — the symbols are those of `SITE_PLAN.md` → Conventions.
- **C8 circuit** — library symbols are referenced as `<use href="#sym-name">` with one of the 19 names of `components/circuit/README.md` (pins on the 10-unit grid; a rotated part uses `transform="translate(x y) rotate(90)"`, never `x`/`y` plus a rotation); `figure.schematic`, `figure.pinout` and `figure.regmap` keep their JSON in a `<template>` child (never a `<script>`: it would be syntax-checked as JavaScript), each with an id and a figcaption; a pinout's pin numbers run 1..N without duplicates and match the package (DIP/SOIC even, QFP a multiple of 4); a register map's fields stay inside `width`, never overlap, use RW/RO/WO/W1C/RSVD, have resets that fit, and every unused bit is a `RSVD` field.

## 6. Writing large pages safely

Write the skeleton (head, hero, first sections) with the Write tool, then append each further section by editing `</main>` into `<section>…</section>\n</main>` in chunks of ≈ 15–30 KB. Extend the single `qc:ready` script by editing it, never by adding a second handler block. Re-run the validator after the last chunk.

## 7. Executed examples (H4)

- A code block may carry `data-executed="YYYY-MM-DD"` and `data-env="Python 3.13"` **only after you ran it yourself** and pasted its real output, unchanged, into the `pre.output` block that follows it (`components/core/code-executed.html`). An example you did not run stays a plain code block labelled "example".
- Run snippets with `python -I <file>` or `node <file>` from a scratch folder (never from the topic folder, never with the site's files on the path); nothing with side effects (no network, no writes outside the scratch folder); keep inputs to the running-example numbers so the output can be checked. Long output: keep the first and last lines and write `… (output shortened)` on its own line inside the output block.
- One executed example per implementation section is enough; `data-env` names the interpreter or tool and its version as printed by `python --version` / `node --version`. The site reviewer re-runs one executed example per page; a mismatch is a must-fix.
- The validator fails `executed example without an output block` and `data-executed "…" is not a date`; it warns on an output block that follows nothing and on a missing `data-env`.

## 8. Consistency lint (H1 — warnings the reviewer reads)

- `validate.py` warns, site-wide, on `<dfn>` terms missing from `glossary.json`, on one glossary term written in two spellings across pages (`Web Mercator` / `web mercator`; hyphenated compound adjectives and file names do not count), on unit spellings (`ms`/`msec`, `s`/`sec`, `km/h`/`kph`, `°C`/`deg C`, `Hz`/`hz`, `kg`/`KG`, `min`/`mins`, `h`/`hr`/`hrs`) and, when `assets/notation.json` exists, on `td.sym` symbols it does not list. Warnings never fail your page; use the glossary's spelling and the SITE_PLAN conventions' units so they stay at zero.

## 9. Flashcards and notes (B4, F1)

- **Flashcards** — a deck is `div.flashcards[data-flashcards]` (`components/study/flashcards.html`): `all`, or a comma list of glossary terms spelled as in `glossary.json`; never write card text into the page — fix a definition in `glossary.json`. `data-tags` is a comma list of the `tags` / `group` values of glossary entries. The validator fails a term that is not in the glossary and a malformed `data-tags`; it warns on a tag no entry carries and on a glossary of fewer than 3 terms.
- **Notes, highlights, bookmarks, resume** — runtime only; write nothing. Highlights are re-found by their text, so a later edit to a sentence orphans the readers' highlights on it: rewrite sentences only when the content needs it. Put `data-no-notes` on `<main>` only for a page whose text is regenerated or mostly interactive; anywhere else it is ignored (warning).
## 10. Code runners (D5)

- A `div.runner` (`components/runner/`) is code the reader edits and runs; an executed example (§7, H4) is code the reader reads. A runner never carries `data-executed`, and an executed example is never wrapped in a runner.
- The H4 rule still binds: a runner's `data-expected` must be real output — run the code as written (JavaScript: `node` with the `data-setup` text prepended; Python: `python -I`, standard library only) and paste its stdout unchanged. Never type an expected output by hand; leave `data-expected` out rather than guess. `ATLAS_RUN_RUNNERS=1 python <PLUGIN_ROOT>/scripts/validate.py …` re-runs every JavaScript runner that has one.
- Every runner has a page-unique `id`, `data-lang="js"` or `"python"`, non-empty starting code, a positive integer `data-timeout` when set, and a `data-setup` that names a `<script type="text/plain">` on the same page. Python runners download Pyodide on first use, so they do not belong on single-format pages (the validator warns).
