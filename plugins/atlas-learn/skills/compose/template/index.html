atlas-learn: from “I want to learn X” to a verified interactive site

atlas-learn interviews you about what you want to learn, researches the topic on the web into a dossier where every source is checked, and builds a multi-page documentation site from that dossier. It runs in Claude Code, in as many sessions as the topic needs, and keeps everything for one topic in topics/<slug>/.

Stages
Insight → brief → research → compose
Formats
Full site, or one self-contained page

Static HTML · diagrams and demos work offline; fonts, maths and media need internet

What atlas-learn is

Asking a model to “write me a guide to map projections” gives a fluent page with unchecked facts, a structure nobody asked for, and nothing to resume when the session ends. atlas-learn splits that request into four stages with a file between each pair. An insight pins down what you want and why. A brief turns it into modules. A dossier holds the verified sources and numbers for each module. The site is written from the dossier alone.

The main agent never researches or writes pages itself. It asks you questions, dispatches subagents by file path, runs a Python gate on what each one wrote, and ticks a row in a short plan only when the gate passes. Because the state lives in files, a run can stop after any module and the next /atlas-learn:go picks up the rows that are still open.

Evidence labels in the sites atlas-learn builds

Established widely deployed practice · Experimental research-stage results, not yet routine · Emerging new products or tools whose maturity is still settling · Discontinued no longer sold or maintained · Verified the source was retrieved and its metadata checked.

What the sources do not establish is marked, never filled in: Not specified the sources cover the subject but not this value · Insufficient evidence too little to state it · Not available in sources no retrieved source covers it · Sources conflict both values are shown · User-provided a value from you, not from a source. Demos label their readouts Model output: computed by the cited model from the inputs you set, not measured.

What it does, and what it does not

Objectives

  1. Turn a vague learning goal into a confirmed insight, a reviewed brief and an approved module list, asking you only about direction, never about formats.
  2. Research every module in parallel and keep only sources that a script or a verifier agent could confirm, with each unverified item marked as such.
  3. Build a consistent, interactive site from one fixed template: navigation, search, maths, diagrams, demos, quizzes, exercises and a trust footer on every page.
  4. Survive interruptions: every stage resumes from the files it left, on the same machine or after a fresh clone.

Boundaries and assumptions

  • Not for quick questions. A one-line factual answer does not need a brief and a dossier; ask Claude directly.
  • One source of facts. Page writers have no web access. A fact the dossier lacks becomes a gap, which sends a researcher back, never a guess.
  • A snapshot. A site reflects the sources on its review date; links point to the originals so the reader can check the current state.
  • Checked by scripts. The gates validate structure, links and syntax; they do not open the site in a browser.

How a topic is built

Each stage has its own command; /atlas-learn:go <topic or slug> runs whichever stage is next, one per call, and --all chains them. Approving the brief always stops to ask you.

  1. Insights — /atlas-learn:collect-insights <topic>. An adaptive interview about your goal and direction. A field scout maps the field in the background; an insight refiner writes the refined insight and derives the policies (depth, source types, verification level). Ends with tmp/INSIGHTS.md confirmed, PLAN.md and topic.json created.
  2. Brief — /atlas-learn:research <slug>. A brief author writes the research brief; a reviewer that never saw the interview reads it with fresh eyes; you approve the outline. Ends with tmp/BRIEF.md approved and the module table in the plan.
  3. Research — /atlas-learn:research <slug>. Module researchers work in parallel, one to three modules each. check_links.py and a source verifier confirm every URL, DOI, arXiv id and video; a consolidator writes the shared parameter sheet, glossary seed and build notes. Ends with tmp/dossier/.
  4. Compose — /atlas-learn:compose <slug>. A page plan, then scaffold.py copies this template; parallel page writers fill the pages from the dossier; validate.py gates every page and a site reviewer reads the result. Ends with topics/<slug>/index.html and pages/.
Limitations

Research needs web search and fetch in the Claude session; when the search quota runs out, researchers stop and record what they could not establish as Not available in sources — nothing is filled in from memory — and the count appears in the plan's caveats and the final report. A single-page topic has a budget of about 250 KB; atlas-learn asks before switching a topic that outgrows it to the full site.

Design principles

01
The main agent only orchestrates.

It holds the conversation, the plan and the gates, and passes file paths, not file contents, to subagents. Research results and page drafts never pass through its context, so a long topic does not crowd it out. How a topic is built

02
Files are the interface.

Subagents cooperate across sessions through markdown under topics/<slug>/tmp/. If a session dies after 9 of 14 modules, the next run dispatches only the 5 rows still open. What each stage leaves behind

03
One source of facts.

Researchers find facts; writers only use them. Writers have no web tools, so a number on a page always traces back to a dossier row and its verified source. Research stage

04
Gates, not trust.

Every agent ends with a RESULT: line, and the main agent flips a plan row only after the matching Python gate passes on the file that line names. Scripts use the standard library only. Install and run

Install and run

Enable

Copy the keys from settings.example.json into the repository's .claude/settings.json: the learning-local marketplace, atlas-learn@learning-local, and the permission allow list. Then run /plugin or restart Claude Code. Needs Python 3.11+ on PATH; node is optional.

Run

/atlas-learn:go how map projections work starts a topic. Each later /atlas-learn:go map-projections runs the next stage. Add --single or --site to force a format, and --all to chain the stages.

Read a site

The left sidebar lists every page; the right rail shows the sections of the current page. Press / to search pages, sections and glossary terms; the glossary defines every atlas-learn term. Diagrams zoom with Ctrl/⌘+scroll and pan by dragging.

# session 1 — interview, then the plan and the topic card
/atlas-learn:go how map projections work

# session 2 — brief, review, your approval, then research
/atlas-learn:go map-projections

# session 3 — scaffold, page writers, validation, review
/atlas-learn:go map-projections

# maintenance: run the tests, refresh the style guide after editing a component
python .claude/plugins/atlas-learn/tests/run_tests.py
python .claude/plugins/atlas-learn/scripts/check_components.py --styleguide
Before you rely on a site

atlas-learn verifies that sources exist and say what the dossier claims; it does not make a topic safe to act on. Check the trust footer at the bottom of every page: it counts the verified sources, names the review date and lists the open gaps.
